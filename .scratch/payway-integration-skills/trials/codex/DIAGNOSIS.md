# Synthetic merchant integration

The merchant keeps the orders, integer prices and demonstration session resolver in merchant-context.ts. Creation accepts orderId and ignores caller-supplied price, currency and owner. Successful creation returns only attemptId and the selected QR string, hosted form HTML or payment-link URL. Gateway implementations must satisfy the recipe's Gateway interface; no live adapter or credentials are loaded. The only callback key is synthetic-trial-key.

## Error diagnosis and evidence limits

Code 104 in the supplied skill's dated September 12, 2026 link-card evidence means "Merchant not enabled token flag": card tokenization requires ABA merchant-profile enablement. It is not a signing problem to bypass. Preserve the endpoint, environment, exact masked error and correlation/attempt IDs when requesting enablement. A hosted form or error page is not successful token creation. The documented failed link attempts produced no token callback; successful linking, token renewal, stored-token charging and recurring cycles remain unproven for a disabled profile. An older generic CLI example in errors-and-debugging.md labels 104 differently; prefer the endpoint-specific evidence and exact returned message, and confirm ambiguous cases with ABA.

Code 1 / 01, "Wrong Hash", indicates a signature mismatch (some endpoints use PTL02). Check the endpoint-specific field order, exact serialized values, timestamp, API-key/environment pairing, Base64 versus hex and mutations after signing. Missing fields can instead cause validation errors. Do not apply callback canonicalization to outbound API signatures. The local SDK verifies signed online callback bodies using the signature header. Correcting a hash does not enable tokenization. These explanations come from the supplied skill references, not fresh gateway probes.

## Ambiguous creation and reconciliation

SQLite commits an attempt before calling gateway.create. A timeout, lost response or invalid artifact leaves it unknown and queued. A second creation returns 409 without calling create again; an existing ready attempt reuses its saved artifact. Restart retains the reservation. Inquiry uses the saved attempt, never callback claims. A transaction ID is a correlation identifier, not a provider idempotency guarantee. Neither a missing callback nor a not-found/PENDING inquiry authorizes another creation.

Online callbacks must have a valid SDK-verified signature. Unsigned link notifications are hints only. Both are durably queued before HTTP 202, without waiting for remote inquiry. Authenticated status requests reconcile through gateway.lookup. The injected provider must bind link proof to the saved link ID and merchant reference; the notification's transaction ID is never passed as authoritative proof. A real link create timeout may lose the link ID: recover from merchant records/ABA, keep the attempt unresolved, and do not guess or create another link.

Only APPROVED proof with matching saved identity, original currency and amount accepts payment. PRE-AUTH is not captured payment; payer-debit currency is not the original order currency. Payment acceptance and the unique per-order fulfillment outbox entry commit in one transaction. Concurrent inquiries and replayed deliveries cannot create a second job.

## Storage and production prerequisites

The Node built-in SQLite store persists orders, attempts/artifacts/link IDs, a deduplicated inbox, reconciliation queue and fulfillment outbox in databaseFile. Seeding on restart preserves existing rows and payment state. Use a private persistent disk, restrictive file permissions, backups and restore checks. This adapter targets one host; distributed/serverless deployment needs a shared transactional merchant database and migrations. Existing saved order prices remain the attempt's authoritative snapshot.

store.pending() exposes reconciliation IDs, store.jobs() exposes durable fulfillment jobs, and store.close() closes the database. This synthetic application reconciles through statusGET; it does not start a background worker. Production requires a scheduled worker that queries pending attempts with bounded retries/backoff and endpoint rate limits, plus an outbox consumer with leasing, completion records and downstream order-ID idempotency. A unique job alone does not guarantee exactly-once external shipping/email effects. Define expiry, late payment, refunds, partial payments and manual-review policies; PENDING does not prove that a QR remains usable.

Before production, replace demo header authentication with real sessions, apply CSRF/origin controls as appropriate, bound and rate-limit requests/queues, configure HTTPS callbacks, monitor reconciliation and secure secrets. Supply a reviewed live gateway adapter with automatic mutation retries disabled, confirmed units/signing rules, merchant-enabled methods/currencies and RSA configuration for links. Host the signed checkout form as intended. Verify current merchant-specific sandbox paid cycles and callback provisioning before go-live. Node must support node:sqlite (Node 22.12 needs its experimental flag).

Validation uses the unchanged acceptance.mjs through npm test: compilation, Express and Next handlers across three routes, server-price enforcement, ownership, pending-versus-approved inquiry, concurrent unique jobs, restart persistence and ambiguous-create recovery. These are synthetic checks, not live sandbox or production evidence. No actual gateway was contacted, no real credentials were accessed, and dependencies were not modified.
