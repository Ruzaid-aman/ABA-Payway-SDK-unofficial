## Quote 1 — official wording (developer.payway.com.kh, 2026-10-05)

The `lifetime` parameter (integer, marked required):

The official example request on the same page uses `"lifetime": 6`.

## Quote 2 — sandbox-pinned probe record (public guide codification)

From the repository's public QR guide at
`docs/guides/07-qr-code-handling.md` (section "Sandbox findings"), verbatim:

> "**QR `lifetime` minimum is 3 minutes — sandbox-pinned 2026-08-30, now
> enforced by the SDK.** `lifetime: 179` -> HTTP 400 code `"04"` ("The given
> data was invalid"); `lifetime: 180` -> success. The API takes **minutes**;
> the SDK accepts seconds, floors to whole minutes (a live QR never outlives
> the merchant's displayed countdown), and **rejects sub-180s values
> locally** with `PayWayConfigError` before any network call (exported
> constant: `QR_LIFETIME_MIN_SECONDS`). `checkout.purchase` is different: its
> `lifetime` is **minutes** (spec min 3, max 43200 = 30 days); sub-3-minute
> values are rejected locally with `PayWayConfigError` (gateway error-69
> parity). QR maximum per the spec is 120 days (not locally enforced; ~27h
> confirmed accepted live)."

## The conflict, stated plainly

- OFFICIAL wording reads: minutes, minimum 3.
- LIVE probes falsify the plain minutes reading: lifetime 3 was REJECTED and
  180 was ACCEPTED (boundary pinned 2026-08-30: 179 -> 400 code "04", 180 ->
  OK). A gateway that truly took minutes with a minimum of 3 would accept 3;
  it did not. The accepted boundary at 180 is equally consistent with seconds
  carrying a 3-minute (180-unit) floor.
- RESIDUAL AMBIGUITY: seconds-vs-minutes-180-floor cannot be settled by
  acceptance probing alone, and no read API returns the QR's expiry, so no
  read-back comparison is possible until such a probe is designed. The
  conflict is therefore recorded, not resolved.

## What is deliberately NOT encoded

- No unit change anywhere. `QR_LIFETIME_MIN_SECONDS = 180` and the seconds
  semantics stay on the generate-qr path; `checkout.purchase` keeps minutes
  (min 3, max 43200) — the coded two-domain split.
- No "fix" may be derived from a single dated observation (audit §19.1:
  `OBSERVED_*` never becomes a universal rule without justification).
- Consumers (request inspection, go-live surfaces) must show this conflict,
  not a resolved unit (audit §48.7: "No QR lifetime unit change (WP-17) —
  the probe has not run. Only the conflict record lands.").

## Enforcement

- `src/constants.ts` — `QR_LIFETIME_MIN_SECONDS` (the 180-second local floor).
- `src/utils.ts` — `validateQrLifetimeSeconds` (rejects sub-180s values on
  the generate-qr path before any network call).
